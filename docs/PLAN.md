规划日期：2026-10-02（Asia/Shanghai）。研究数据时间统一使用 UTC。

**项目定位：用可复现的链上数据，评估 DeFi 交易激励结束后的地址参与度与奖励支出。**

首个案例建议：**GMX V2 / Arbitrum / 第一轮 STIP 交易返佣**。

英文案例题目：**After the Rebates: Trader Retention on GMX V2 Following Arbitrum STIP**。

本文件是实施计划。已查阅官方活动材料、岗位要求、数据文档及源码入口；尚未采集交易数据、验证历史 API 覆盖或计算研究结果。所有里程碑、工时与质量门槛均为本项目的建议，不是已完成的工作。

**4. 研究问题与可交付的回答**

主问题：**返佣窗口内开仓或加仓的地址，在返佣结束后的第 24–30 日，有多少再次开仓或加仓？**

配套问题限定为四个：

1. 首次使用 GMX V2 的地址与既有地址，后续表现是否不同？
2. 不同入组周、不同事前交易规模的地址，回访表现有何差异？
3. 同一批成熟地址在结束前后的交易活跃度与手续费水平保留了多少？
4. 若返佣可以逐地址归属，每个后续回访地址对应多少已分配返佣？

先写待检验的假设，例如“晚期入组地址的回访率更低”“总体交易量由少数大地址主导”，再分析。假设不成立也能形成有价值的研究结论。

数据只能支持地址行为。不能把地址称为人数，也不能把活动期间的新地址直接解释为由活动带来的增量用户。

**5. 时间、队列和合格事件定义**

设 T 为 E 之后第一个完整 UTC 日的起点；如果 E 恰好为零点，则 T=E。设 U 为 E 所在 UTC 日的零点。E 非零点时，等长日窗口省略不足一天的边界部分，并披露。

主要明细覆盖 [S−56 天, T+60 天)，另获取 GMX V2 部署以来的账户首次交易信息。初始下载分区先用一天，再扩展到一周；不从全链无筛选扫描开始。

| 队列 | 定义 | 用途 |
| --- | --- | --- |
| C：活动队列 | [S,E) 至少一次成功执行、名义规模增加的开仓/加仓地址 | 主指标固定分母 |
| 新 V2 地址 | C 中首次 GMX V2 永续交易发生在 [S,E) 的地址 | 新旧分层；需要完整首次交易历史 |
| 既有 V2 地址 | C 中首次 GMX V2 永续交易早于 S 的地址 | 新旧分层 |
| 入组周 | 地址首次符合 C 的事件所在 UTC 周 | 展示活动暴露时长差异 |
| C_m：成熟子集 | C 中首次 V2 交易早于 U−30 天的地址 | 结束前后等长强度比较 |
| 已分配返佣子集 | 有可验证账户与 epoch 分配额的 C 内地址 | 奖励子组分析，不能偷偷替换 C |

若无法拿到部署以来的完整历史，将“新 V2 地址”改名为“观察窗首次出现地址”，列出历史开始时间。没有该历史不妨碍发布 C 的整体回访指标。

基础合格事件必须成功执行、size_delta_usd > 0；仅补充抵押品、取消订单、失败交易、领取奖励、清算、ADL 不算开仓/加仓。一般减仓单在广义交易指标中保留，清算和 ADL 仍排除。

地址使用协议订单/仓位的 account。GMX 用户创建订单后由 keeper 执行，执行交易的发送者不等于仓位所有者。订单、执行、仓位变更是同一行为的不同记录，不能简单相加。

基础指标衡量“已执行交易回访”。严格版本再要求对应订单创建时间 >= E，避免把返佣停止前创建的限价单在后来成交视为新的参与决策。创建时间缺失时单列缺失量，不声称已测量严格回访。自动化策略仍可能满足严格定义，因此也不称“真人留存”。

**6. 指标字典：一项主指标、必要的解释指标**

记 I(i,W)=1 表示地址 i 在窗口 W 至少一次合格开仓/加仓，否则为 0。所有比例同时显示分子 n、分母 N 和百分比；分母为零时显示 N/A。

| 指标 | 确切定义 | 解读边界 |
| --- | --- | --- |
| 主指标 R30 | W30=[T+23天,T+30天)；Σ(i∈C)I(i,W30) / \|C\| | 第 24–30 日开仓/加仓回访率，不是“30 天内回来过” |
| 30 日累计回访率 | 窗口 [T,T+30天) 内至少一次合格开仓/加仓的 C 地址 / \|C\| | 可能只在第一天回来过 |
| W30 持续活跃率 | W30 内至少 2 个不同 UTC 日有合格事件的 C 地址 / \|C\| | 不能证明是自然人或排除刷量 |
| 广义交易回访率 | W30 内至少一次自主交易，包括正常减仓的 C 地址 / \|C\| | 与开仓/加仓口径一起展示 |
| 严格新订单回访率 | R30 的事件额外要求订单创建时间 >= E | 仅在关联和历史字段足够时发布 |
| 60 日回访率 | [T+53天,T+60天) 中的合格回访地址 / \|C\| | 数据完全覆盖且后续奖励边界明确才发布 |

前后活动强度采用同一个成熟队列 C_m、等长窗口 B=[U−30天,U)、P=[T,T+30天)。

- 活跃地址日比例 A(W) = C_m 在 W 中所有地址的活跃日数之和 / (30 × |C_m|)。
- 每地址日交易手续费 F(W) = C_m 在 W 中的同口径交易手续费 USD 总和 / (30 × |C_m|)。
- 报告 A(P)、A(B)、A(P)/A(B)；手续费同理。始终保留零活跃地址，基线为零则比例为 N/A。
- 主口径采用同一类已执行事件。旧挂单排除另报，不能只调整后期而不披露比较口径差异。
- 交易手续费使用奖励抵扣前、明确可核对的费用字段；不把 funding、borrowing、gas、price impact 混成交易手续费或协议净收入。字段不充分则保留活跃地址日指标，暂不发布手续费结果。

返佣成本为条件交付：K(C)=C 在 [S,E) 赚取的、可归属的交易返佣分配额 / C 中 W30 回访地址数。分子包含 C 内最终未回访地址得到的返佣，不能只统计回访者的奖励。

保留 ARB 原币金额；USD 估值预先固定到赚取 epoch 的价格口径，已支付成本另用付款日估值并分别命名。分配额、支付额与未领取额不可混用。只能拿到整体交易返佣支出时，报告整体支出，不计算新地址或某个子组的单位成本。K 是观察到的单位回访地址支出，不是因果获客成本或 ROI。

**7. 研究方法和稳健性**

第一版采用固定队列与事件时间图。结束前、结束后的简单差异不代表因果，既有地址、新地址以及其他协议也不会自动成为随机对照组。

必须完成三项对照：

1. **入组周与新旧地址分层。** 同时展示每组 n/N，说明短暴露期与完整历史的限制。
2. **大地址影响。** 按 E 前活动期交易规模固定排序，比较全体与剔除前 1% 地址的结果；公开小样本取整规则，不能按事后表现挑选被剔除地址。
3. **事件定义。** 对比开仓/加仓与广义自主交易，1 个活跃日与 2 个活跃日；可关联订单时再比较是否排除旧挂单。

将交易大赛、钱包任务、网络升级、奖励强度变化标在同一时间线。对 2024-04-10 及之后定义额外完整观察窗口，并明确这是不同的日历窗口；不能删掉重叠日期后继续沿用原来的 D30 名称与分母天数。重叠活动的参与者名单若不可得，保持未知，不能凭金额命中任务阈值就认定参与。

默认不为全量历史地址机械添加二项式置信区间。主要展示真实计数、定义敏感性与分组差异；这些更能说明本研究的误差来源。若后来研究外推或因果效果，再定义目标总体、对照与统计假设。

不把未知地址标记为真人，也不把高频交易、套利或同源资金单独当成刷量证据。第一版保留“未知”标签，不制作无依据的 Sybil 分数。

**8. 数据来源与获取路线**

| 证据 | 优先来源 | 验证方式 |
| --- | --- | --- |
| 奖励机制及 earning epochs | GMX/Arbitrum 官方提案、周报和最终报告 | 对照分期规则、付款记录、修改公告 |
| 交易、订单与账户字段 | Dune 协议解码数据，或 GMX 官方 GraphQL | 抽样回到链上事件，核对 account 与类型 |
| 奖励分配与支付 | 官方 epoch 清单、分发交易与相关事件 | 分用途、逐期核对总额与账户 |
| 价格 | 已选主数据源的历史价格；明确来源 | 核对日期、单位与缺失，不用当前价格代替 |
| 指标交叉检查 | GMX 官方引用的 Dune 看板 | 先对齐链、版本、产品、日界线与费用定义 |

**推荐路线 A：Dune 查询 → API 导出 → Python / DuckDB → Notebook / 看板。** 条件是账户能执行和导出所需查询，且协议历史字段足够。查询先按链、协议、日期过滤；Dune 负责链上筛选和聚合，Python 负责获取、验证与分析。

**备选路线 B：GMX GraphQL → Python / DuckDB SQL → Notebook 导出的静态报告。** 官方文档公开了 Arbitrum Subsquid 入口，但 2023–2024 年历史覆盖、分页方式、订单关联字段和限流仍需在第一阶段验证。B 路线保留 SQL 能力展示；Dune 作为小范围对照或后续看板，不能把未执行查询写成已验证作品。

两条路线第一周选定一条作为主来源，另一条仅作小样本核对；不维护两套完整 ETL。Dune 的 dex.trades 是现货交易路径数据，不能默认拿来替代 GMX 永续交易事件。

截至本次查阅，Dune 文档说明 API 需要有效试用或付费计划，查询和导出消耗额度。因此不承诺全量数据免费获取，也不依赖“免费无限 CSV”。建议自设人民币 0–300 元的试跑预算上限；这是预算控制建议，不是套餐报价。先估算全窗口扫描与导出成本再决定是否购买，超限优先减少字段、分区和重复执行。

数据入口：[GMX 官方 GraphQL](https://docs.gmx.io/docs/api/graphql/)、[GMX 官方引用的 STIP 看板](https://dune.com/gmx-io/gmx-stip-dashboard)、[Dune API 导出](https://docs.dune.com/api-reference/executions/endpoint/get-execution-result-csv)、[Dune 计费](https://docs.dune.com/api-reference/overview/billing)、[Dune dex.trades 定义](https://docs.dune.com/data-catalog/curated/dex-trades/evm/dex-trades)。

**9. 最小数据模型与代码结构**

只保留能直接支撑研究的表。以下是本项目拟建的标准表，不是声称已存在的上游表名。

| 表 | 粒度/唯一键 | 核心字段 |
| --- | --- | --- |
| campaign_epochs | 活动 × 奖励用途 × epoch | earning_start/end、payment_time、规则、来源 |
| trade_actions | 单条执行事件 | chain_id、tx_hash、log_index、account、order_key、事件类型、时间、market、原始金额与单位 |
| reward_allocations（条件） | 活动 × earning epoch × account × 奖励币种 × 分配类型 | 分配量、已支付量、支付记录、归属依据 |
| wallet_daily | UTC 日期 × account | 合格事件数、广义事件数、严格事件数、费用、名义交易规模 |
| wallet_cohorts | account | first_seen、first_qualifying、入组周、历史覆盖、新旧标签、事前规模组 |

一个订单涉及多条事件时，先按事件唯一键去重，再按 order_key 建立关系；重复收录同一行为的不同数据源不相加。上下游一对多连接必须检查是否放大行数。金额保留原始整数或精确十进制值及 scale，不把所有 GMX USD 字段都假设成 ERC-20 的 18 位小数。

**10. 最小质量检查与复现标准**

保留一个可直接运行的 checks.py，不引入庞大测试框架。它同时检查一个小型合成样例与真实汇总数据。

| 检查 | 失败时的处理 |
| --- | --- |
| 事件唯一键无重复；账户、时间、事件类型等必填字段完整 | 阻止正式指标生成 |
| 分页结束、分区覆盖、最早/最晚时间、空分区均有记录 | 缺失日期不能当成零交易日 |
| 订单关联不放大事件数；keeper 与 account 分离 | 修正归属和 join，再重算 |
| 合成样例覆盖窗口边界、D30 与累计回访差异、零分母、清算、只减仓、旧挂单、晚入组 | 错一项即停止交付 |
| 每组留存分子 ≤ 分母；固定队列不随是否回访变化 | 修正 cohort 与筛选顺序 |
| 所有 R30 / R60 均有完整后续覆盖；缺失价格保留缺失 | 覆盖不足的指标不发布 |
| 分层可加总项与总体一致；地址去重项按集合重算 | 不直接相加可能重叠的独立地址数 |
| ARB 分配、支付与报告总额按用途核对；差额有解释 | 不能归属的成本指标暂不发布 |

抽检建议：至少 20 个账户、30 条跨活动前中后及不同事件类型的记录，逐条核对归属与单位。抽检不能证明全量无错，因此仍需要全量不变量检查。

另选 7 个日期，对照一个同口径来源的交易量/费用或事件数。建议以 1% 作为“触发调查”的初始差异门槛，属于项目自定规则，不是行业标准；低于门槛也不能自动证明正确。若口径不同，写清差异，不强行把数调到一样。

复现分两级：

- **无密钥阅读/重绘：** 从已发布、允许再分发的冻结汇总结果生成图表。小样本只能演示管线，不能复现全量结论。
- **完整重算：** 按记录的参数获取全量数据并重建指标；明确需要的数据权限、预计费用与版本。若原始来源修订，记录新结果与旧快照的差异。

如果允许发布完整的地址日明细，可支持离线重算留存；否则清楚标注只有汇总重绘可离线完成。重复运行相同冻结输入应产生相同结果；不要让同名“latest”结果替换历史研究输入。

**11. 看板和报告设计**

推荐 Dune 作为公开看板；没有合适执行权限时，用同一份指标输出静态 HTML/Notebook 页面。第一版无需另写一个 Web 应用。

看板只保留四个视图：

| 视图 | 回答的问题 | 图表/内容 |
| --- | --- | --- |
| Overview | 活动结束后保留了多少参与？ | cohort N、R30 n/N、累计回访率、活动时间线 |
| Cohorts | 哪些地址回来？ | 入组周 × 结束后周热力图、新旧地址比较、每组分母 |
| Activity & Cost | 回访质量与支出如何？ | 活跃日分布、成熟队列强度、条件性成本图 |
| Methodology | 结果为什么可信？ | 指标字典、来源、覆盖、检查结果与局限 |

建议最终 5 张核心图：活动及重叠奖励时间线、结束后周回访热力图、新旧地址回访比较、事前交易规模与回访关系、不同定义的稳健性对照。第 6 张奖励成本图只在数据足够时添加。

每张图写清窗口、分母、样本量、单位、来源和数据截止；缺失与零值用不同表示。颜色要有文本/图例辅助，避免仅靠红绿区分。热力图的横轴明确是“距活动结束的周数”，不能与“距首次交易的周数”混用。

英文报告建议 1,500–2,000 词，约 4–6 页阅读量：研究问题与摘要、激励机制、数据与方法、主要发现、稳健性、局限与业务含义。摘要和结论在结果产生后写，不先填写预想数字。

建议按证据条件表达业务含义：若新增地址很多但后续持续活跃弱，讨论与持续参与绑定的奖励规则；若费用和交易规模高度集中，讨论奖励上限或分层预算；若结论随口径大幅变化，优先建议改进监测。它们是待检验的建议路径，不能现在就宣称应该削减或加大奖励。

**12. 4 周执行计划与验收**

默认前提：一人，有基础 SQL/Python，每周约 15–20 小时，总计 60–80 小时。完全从零学习时按 6–8 周安排。下表的工时是估算，日期随实际启动日平移。

| 阶段 | 工作 | 工时估算 | 必须交付 | 通过条件 |
| --- | --- | --- | --- | --- |
| 第 1 周 | 活动核实、接口/权限试跑、字段映射、一天到一周样本、全窗成本估算 | 15–20h | 来源表、时间线、数据字典、首批样本与抽检 | 可解释的 S/E；account 与类型可用；历史覆盖与预算可接受 |
| 第 2 周 | 全量分区获取、标准化、首次出现、固定 cohort、R30 和累计回访 | 15–20h | 可运行管线、checks.py、冻结数据与首轮结果 | 关键质量检查通过；n/N 与窗口正确；重复运行一致 |
| 第 3 周 | 入组周、新旧和规模分层、稳健性、费用/返佣条件分析、看板 | 15–20h | 5 张核心图、研究发现草稿、看板初版 | 每条发现可追溯；未知数据显式保留；成本归属不混用 |
| 第 4 周 | 英文报告、复现演练、文档、展示与面试准备 | 15–20h | 完整仓库、报告、可访问展示、3 分钟演示提纲 | 新环境可按文档复现约定层级；所有链接、单位与结论核对 |

依赖顺序：**活动与数据可行性 → 字段和指标冻结 → 全量处理 → 研究结论 → 展示与投递。** 前端和报告排版不应挡住数据可行性验证。

第一周最多投入 3 个工作会话验证最关键的数据路径。若失败，按下面的规则调整，不继续盲目补工程：

| 问题 | 调整决定 |
| --- | --- |
| Dune 不可用或费用超预算 | 验证 GraphQL 主路线；不绕过数据平台权限 |
| GraphQL 缺历史，但 Dune 覆盖完整 | 使用 Dune 主路线并冻结导出 |
| 无法准确核实返佣 E | 先做按周活动队列描述；暂停精确“结束后 D30”结论，明确该项尚未完成 |
| 无法区分账户与 keeper，或核心事件类型缺失 | 核心研究不通过；更换经小样本验证的活动案例 |
| 逐地址奖励分配不可得 | 保留留存研究，删除单位返佣成本承诺 |
| 部署以来的首次交易历史不可得 | 采用“观察窗首次出现”标签，不声称协议新用户 |
| 第 3 周仍在修基础数据 | 暂缓 60 日与成本扩展，完成核心 R30、分层与报告 |

候选备选为 Notional V3 / Arbitrum 单一池的 STIP，但它需要改成资本/头寸留存设计，不能直接套 GMX 的交易回访指标。仅在 GMX 核心数据不可得时重新核查。[Notional 官方 Addendum](https://forum.arbitrum.foundation/t/final-notional-stip-addendum/23393)

**13. 开工前两次工作会话**

第一次（约 3–4 小时）：阅读官方材料，记录返佣的赚取/支付时刻、调整、重叠活动；核实 Dune 账户执行/导出权限；试读一个历史日的 schema 和数据；列出 account、order_key、事件类型、规模、时间与费用的映射。拿不到字段时不要先写通用采集框架。

第二次（约 3–4 小时）：抓取一个完整历史周；沿链上记录抽检 keeper/account、开仓/减仓/清算与金额单位；计算每天事件数和唯一账户数；估算全窗口导出量；冻结主数据源与 MVP 字段。两次会话后应能判断项目是否可行，而不只是有一个仓库首页。

剩余第一周完成活动边界与少量返佣记录核对、研究问题和指标冻结，再开始全量处理。

**14. 最终完成标准**

- [ ] 一个真实、范围明确的 GMX V2 / Arbitrum 历史案例；S/E 的依据或未解决限制清楚。
- [ ] 可运行的获取与分析流程；SQL/Python 有用途明确的注释。
- [ ] 主 R30、累计回访、必要分层和三项稳健性比较完成。
- [ ] 数据检查可运行；样本、全量、缺失与零值不混用。
- [ ] 至少 5 张可读图；有公开看板或静态结果入口。
- [ ] 英文 README 和英文研究报告，主要结论可追溯到冻结结果。
- [ ] 来源、单位、历史字段变化、奖励重叠和地址局限已披露。
- [ ] 无密钥展示与完整重算的能力边界、数据权限和费用已写清。
- [ ] 第三方数据/代码保留来源和原有许可，自有代码选择明确开源许可。
- [ ] 一次从干净环境开始的复现演练完成，展示链接有效。

完成标准不包含“激励效果必须显著”“留存率必须高”或“仓库必须有多少星”。研究结论为负或不确定，也可以是优秀作品。

**15. 投递与面试展示**

GitHub README 首屏顺序：一句研究问题 → 数据支持后的三条发现 → 一张核心图 → 看板/报告/复现链接 → 方法局限。仓库名用 IncentiveScope；案例副标题明确 GMX、Arbitrum 与历史年份。

三分钟演示：30 秒解释问题和激励机制，60 秒展示主结果及分层，60 秒解释地址归属/奖励重叠/稳健性，30 秒给出有边界的业务建议。

简历英文句式（完成后替换占位内容，未验证前不填数字）：

> Built IncentiveScope, a reproducible SQL/Python study of [N] GMX V2 trading accounts on Arbitrum; measured post-STIP repeat trading across [K] weekly cohorts, validated account attribution, and published an interactive dashboard and research report.

准备回答：为什么不用 tx.from；为什么地址不等于人；为何 D30 和累计回访不同；为何旧挂单与只减仓需要单列；为什么付款日不等于奖励结束日；为何新地址不代表新增用户；为什么没有给出因果 ROI；奖励重叠怎样限制结论。

第二个案例或因果研究放在第一版完成之后。若补充更近的案例，应选择已经结束且至少有 30 天完整后续数据的活动，先验证资料和历史字段，再考虑是否抽取复用模块。

**第一步的验收成果是“可验证的活动时间线 + 一周真实交易样本 + 明确的账户字段”，随后再扩展为完整研究。**
